# Windows 共享内存发送进度诊断

共享内存队列持续增长时，应先区分“消费者确实来不及处理”和“发送线程反复丢失执行机会”。后者即使每条消息很小，也可能耗尽发送预算。扩大队列只能延迟溢出。

## 2026-10-22 修复

1. Win64 的进程存活查询原来通过释放 GIL 的 ctypes 接口调用。QMT 回调繁忙时，每次本机查询返回后都可能重新等待 Python 执行权。`OpenProcess`、零等待的退出状态查询、`GetProcessTimes`、`CloseHandle` 改为保留 GIL 的即时查询；真正的阻塞等待仍释放 GIL。32 位调用约定保持原状。
2. 跨进程互斥的零等待探测失败后，原来立即 `sleep(0)`，会把短临界区竞争放大为一次线程调度等待。现在先进入最多 1 毫秒的内核等待；仍不成功才在未持有互斥锁时让出执行权。总截止时间不续期，同进程持锁线程仍有机会运行。
3. 同一次消费者维护中，按 PID 和创建时间对存活查询去重；下一次维护重新查询。清理仍匹配完整的槽位、身份及 token，不缓存跨轮的存活结论。

发送预算在成功提交前耗尽时，消息必须留在本地队列；维护期限也不会假装已经完成而向后推进。旧逻辑因此可能在下一次重试继续探活、继续失去执行权，新行情则不断入队，最终达到字节容量上限。这解释了为什么“发送线程还活着”和“大部分原生查询很快”仍可能伴随持续积压。

这次没有修改共享协议、消息内容、确认顺序、队列容量、成交归属或恢复门禁。

## 诊断字段

原始推送通道 `status()` 新增以下本地计数，读取不会触发新的探活：

| 字段 | 含义 |
| --- | --- |
| `peer_probe_count` | 实际执行的外部进程存活查询次数 |
| `last_peer_probe_seconds` | 最近一次存活查询墙钟耗时，单位秒 |
| `max_peer_probe_seconds` | 本通道实例存活查询最大耗时，单位秒 |
| `liveness_timeouts` | 探活或探活后的提交锁耗尽原操作预算次数 |

开启 `BIGQMT_DEBUG=1` 后，`push_liveness_timeout` 日志区分 `peer_probe` 与 `commit_lock`，每秒最多一条。默认不输出该调试日志。Windows 单调时钟可能使短调用计时为零，不能把零解读为无成本。

继续结合缓冲发布器的 `local_pending`、`oldest_pending_seconds`、`shared_committed`、`backpressure_count`、`last_backpressure` 和 `overflow_count` 判断进度，不能只看发送线程是否存活。`healthy=true` 本身也不证明所有积压已经清空。

## 可复现压力测试

以下命令从仓库根目录运行，使用独立命名空间和合成数据，不连接任何交易账户：

```bash
python benchmarks/shm_peer_liveness_benchmark.py --rounds 60 --switch-seconds .1 > peer-liveness.json
python benchmarks/shm_push_contention_soak.py --seconds 300 --rate 80 --consumers 3 --gil-hold .05 --gil-gap 0 --output soak.json
```

第二个测试在 Windows 或 Linux 上使用真正独立的消费者进程：

- 行情及合成买入、卖出、撤单事件分别进入两条正式推送日志。
- 持续 CPU 竞争、慢回调、稳定订阅身份重连同时存在；发送端全程不重启。
- 逐字段核验双精度数值、超过双精度精确整数范围的整数、序号、完整性、重复和顺序。
- 停止生产后仍保留 CPU 竞争，确认队列能自行排空；检测到溢出、字段错误或无法排空时返回非零退出码。

这不是正式下单业务测试。正式业务另用 qmt-grpc 仓库的 `tools/shm_business_soak.py`，经过真实 dispatcher、模拟终端及独立账务检查器验证买卖、撤单与重连。

## 验证范围

2026-10-22 的 Windows 对照中，旧代码在 100 毫秒线程切换竞争下，60 次存活查询有 20 次超过 200 毫秒；修改后为 0 次。仅修复存活查询仍无法通过持续竞争测试，随后定位并修复上述互斥等待顺序。

最终 Windows 五分钟持续竞争测试，23,945 批行情和 2,394 条合成交易事件由三个消费者完整接收，行情队列峰值 100 批，最终积压为零。测试包含 1.5 秒慢回调和两次重连；本次没有溢出或背压重试。

历史故障发生时未开启完整阶段日志，因此这证明了两处能复现同类积压的实现缺陷及修复效果，不能反推出当时每个线程的精确调用栈。有限压力测试也不代表生产 QMT 已完成整日验收；生产重载后仍需核验实际模块、通信健康和完整对账。
